# Petros Learn — final M3 teacher refinement

15 October 2026, Asia/Kolkata. Implemented in the existing institution portal and left running for manual inspection. The four steps remain **Choose material → Review lesson → Preview activities → Save & submit**. M4 has not started. These are controlled, source-backed engineering proposals, not genuine AI-generated or academically approved lessons.

The current implementation, [previous teacher redesign report](m3-teacher-ux-redesign.md), [M3 verification report](m3-learning-proposals.md), implementation-plan §§3.1, 3.3, teaching-engine integration and M2-G/M3/M4/M5 boundaries, and blueprint ownership boundaries were read before changes. The extensively modified checkout was preserved without reset, clean, stash, staging or commits.

The focused changes are:

- **Distinct student tasks.** Cloud responsibility classification uses actual table cells as unsorted cards and the actual consumer/provider column headings as categories. Teachers can inspect IaaS, PaaS and SaaS without submitting answers. The virtualization comparison uses its own source passage and logical/physical concept headings. English asks the learner to identify a claim, cite evidence and explain its support; its second activity asks what the survey supports and which assumption remains uncertain.
- **A consistent preview hierarchy.** Title, short instruction, read-only task layout, expected student response, then source inspection. The responsibility table is available in the source drawer rather than duplicated beside a second conceptual board. Empty response areas are labelled as planned work; no learner work, correctness, tutoring or execution is fabricated.
- **Bounded existing rendering.** The existing `ActivityPresentation`, `NativeSourceTable`, `m3ActivityPreview`, public `ContentUnit`/teaching-block schemas and registered families are retained. The compiler limits concepts and quotations to the objective/activity source intersection. Comparison does not manufacture directional edges. Controlled fixture co-occurrence relationships were removed. Legacy proposals with additional activity citations receive an alignment warning. Unsupported execution remains unavailable, and only registered structural alternatives are offered. There are no subject-name branches in runtime presentation or outline generation; subject wording remains confined to the explicit test/demo fixture builder.
- **One primary lifecycle label.** Backend proposal state and current review projections determine the lesson status. “Review your lesson before submitting” replaces readiness language; successful submission uses “Your lesson has been submitted for review.” Revision numbers moved out of the primary status. Student availability remains a separate restriction.
- **Clear objective actions.** “Keep this objective” still sends `accept_objective`, recording only a draft choice. Disabled movement/removal/keep actions have explanations. Menus open into available space and scroll when necessary. Source inspection offers a choice between the lesson’s cited sections; closing restores the trigger and scroll. The source button remains focusable during its read, while further activation is blocked.
- **Less navigation effort.** The current step remains visible below the portal header; footer actions remain in a consistent location. Objective/activity selection survives Back/Next and reorder. Existing visited-panel retention, conflict recovery, advanced inspection, historical revisions, qualified review and private-review separation remain in place.
- **Teacher presentation.** UUID subject codes are hidden beside the class subject; backend identifiers remain intact. Hashes and generator pins remain in advanced source/provenance details. “Sample lesson — prepared from test data” remains visible. Normal demo chrome no longer names the implementation milestone.

Files changed are the existing institution teaching page; `petros-learning-proposal.tsx`, `petros-lesson-presentation.tsx`, `petros-learn.module.css`, `petros-teacher-guidance.tsx` and their tests; the existing M3 public preview compiler; and the controlled proposal fixture/spec. Separate final demo, browser, accessibility, regression and evidence-guard scripts were added under `apps/api/scripts/`. No database migration, production permission policy, provider route, assessment/session engine or design-system replacement was introduced. [Starting state](m3-teacher-ux-final-evidence/starting-git-status.txt) and [baseline copies](m3-teacher-ux-final-evidence/baseline/) are retained.

The count contradiction was caused by the **old isolated demo endpoint returning `{ students: [], goals: [] }` unconditionally**, while the real teaching reader counted two actual fixture class records. The real guidance reader filters currently enrolled students under institution/class/campus/teaching authority. Both fixture students are enrolled and permitted. The final harness calls that actual guidance reader and returns two recipients. The header’s legacy reader counts the class list, so the UI says **“2 students on the class list · 2 permitted recipients for learning goals”**, rather than assuming every class record is enrolled. A separate explanation says assignment is disabled in this isolated lesson preview. The demo POST explicitly returns **403**; it does not create an assignment or return a fake receipt. Production recipient authorization and assignment behavior were not weakened.
