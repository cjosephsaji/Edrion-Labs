## 2. Exact candidate schema/security changes

`apps/api/scripts/petros-v2-readiness-repair.sql` is a **guarded rehearsal artifact outside automatic migration directories**. It requires a per-transaction temporary marker, a randomly generated `petros_m0r_<24 hex>` database name, the newly initialized cluster's matching data directory and a Unix-socket connection. It rejects unmarked/configured targets. It runs atomically with a 2-second lock timeout and 15-second statement timeout.

It creates the four existing document-learning tables with their declared columns, PKs, eight original unique/lookup indexes and original progress bound. It restores the outline column and adds:

- Composite tenant/source/preparation/first-lesson FKs, including student/institution and knowledge-item/owner relationships. The circular first-lesson FK remains deferred. Supporting composite unique indexes include existing knowledge/material dependencies.
- Positive source version, SHA-256 format and canonical source-key checks. Existing conflicting index definitions abort the transaction; their names are not accepted as proof of equivalence.
- FORCE RLS; strict owner policies on installed direct-owner Petros and knowledge tables; parent policies for pages/session children; tenant/user policies for portal conversations; scoped assignment-recipient reads.
- Current student/account status, source revocation, object readiness, material/class/course membership, source version and extracted-page checksum checks. Shared authorized course material remains readable through the current learner's own matching source copy. Withdrawn enrollment/source/account or a changed checksum denies subsequent access.
- A non-owner, non-superuser, non-BYPASSRLS application role with no memberships/admin/schema-create privilege. A separate document-worker role gets explicit table/column grants, not `ALL TABLES`, and cannot write qualifications, owner identities, V1 sessions or operations projections. Job work additionally requires a matching preparation ID and active owner path.
- Immutable document extraction/history and published lesson content protections. Source/preparation/artifact/path document dependencies use restrictive deletion rather than destructive cascades; withdrawal remains a logical access decision. This retention change requires review before new document rows are admitted.
- Ordinary-role access to public artifact columns only. Private lesson answers remain worker/server-side. Existing qualification/review/evidence protections survive the final grants overlay.

The schema repair does not rewrite source snapshots, transcript/answer payloads, old command responses, scores, marks, IDs or ledger history. No V2 content/concept/task/evidence tables, engine pin or turn epoch are introduced.

Custom GUCs are a trusted-server scope mechanism. They do not authenticate a principal against arbitrary SQL from someone holding the application secret. Existing API permission guards and live session verification remain authoritative. Existing security-definer functions are inventoried; current IDs-only dispatchers and admitted pack/runtime projections are retained for V1 compatibility, not treated as unrestricted worker authority. The document worker cannot execute the existing operations or due-question dispatcher functions.

## 6. Deployment risks and rollback/restore plan

**No rollout is authorized or scheduled.** Before any separately approved staging run: verify the target identity, installed DDL/ledger and reservation again; complete the blocked role-aware service integrations; review actual permissions/worker credentials; capture a database backup plus original/derived assets, manifests and restore instructions. Stop/drain affected writes/workers so pool/DDL/security ordering cannot straddle different credentials or policies. If authorized later, the ordered reviewed package is the known idempotent pending `0233` statement, new `0234` repair, final `zzz_grants.sql`, final `zzz_rls.sql`, and existing visual backfill. Unlike the Phase-A fixture, normal approved migration execution appends real new receipts. Apply statement/lock bounds; roll back the transaction on lock contention or unexpected object/history shape. Build indexes/FKs can lock existing knowledge/material tables; estimate sizes/duration on staging. FORCE RLS may reveal formerly hidden unscoped callers. Source checksum revalidation adds indexed page reads and needs staging latency measurements. Published-lesson immutability rejects the current content-changing upsert path. These are deployment gates, not reasons to loosen policies.

For a failed transactional repair, roll back and verify all old receipts and role/catalog state. For failure after standalone SQL or credential cutover, stop affected traffic/jobs; use the captured exact pre-change role/ACL/policy state and database-plus-assets snapshot to restore an isolated target and verify it before switching. The additive document schema can remain unused while traffic is contained. Do not drop newly populated tables, erase ledger rows, disable immutability or restore the superuser credential as a quick application rollback. Retention withdrawals should hide sources while retaining authorized history; any physical deletion/retention workflow needs a separate review. Production restore and post-cutover data reconciliation require explicit approval and a reviewed write window.

After any separately approved deployment, rerun the read-only M0 inventory, real role denials and authenticated V1/pilot journeys. Fixture pass counts alone cannot clear readiness.
