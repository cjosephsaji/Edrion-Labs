# Petros V2 — M3 learning proposals

**14 October 2026, Asia/Kolkata. Authorized isolated engineering implementation. Full educational release acceptance remains OPEN.** M4–M8 were not implemented. No configured application database, staging/production migration, paid inference, real qualification, learner assessment, grading or student publication was used.

## A. Executive summary

M3 adds a functioning institutional teacher workflow backed by actual M2 extraction records: select a current source, inspect its status, construct a bounded source outline or inspect a controlled proposal, edit observable objectives, inspect native evidence, compare activity candidates, save immutable revisions, submit the exact draft to the academic owner, inspect distinct review decisions and check release restrictions.

The real gateway boundary is registered as `teaching.propose`. An internal authorized worker entry exercises actual restricted-role reservations, controlled transport, usage settlement and durable proposal persistence outside a provider transaction. The public portal request for gateway inference is **503/default-denied** because no real source-sharing/spending/provider authorization has been established. Source outlines are labelled **Engineering-generated source outline**; test proposals are **Controlled fixture**. Neither represents genuine semantic understanding.

All 46 final restricted-role M3 tests passed (30 source/gateway cases plus 16 private-review cases). The positive scope test uses two synthetic staff actors, a current synthetic qualification, actual curriculum context and an explicit synthetic current-source ownership/teaching handoff. It records an **isolated teaching-scope authorization manifest**, while student publication remains blocked. A separate private-path fixture reviews all nine source-pinned private families through the existing candidate/review owners and records only opaque family references in an isolated manifest. It is not a real lesson release or academic approval. The teacher browser path passed 18 checks, including 360px containment; the qualified private path passed 11 separate checks. Human usability acceptance remains pending.

Historical preservation is also failed for two unrecovered database receipts; see P. This is a reviewable engineering slice, not a claim that all 34 acceptance criteria or full-release gates are satisfied. All 34 requested criteria are evaluated in [acceptance-evaluation.json](m3-evidence/acceptance-evaluation.json), with limits separated from passing mechanical tests. Genuine semantic quality, real instrument validity/exposure, ordinary independent-reviewer source-sharing and representative-teacher testing remain open; see Q and R.

## C. Proposal contracts

M1 `petros.v2.proposal.v1` remains compatible. Additive versions are `petros.v2.learning-proposal.v1`, model contract `petros.m3.proposal.v1` and review receipt `petros.v2.scope-review.v1`. API-only private preparation uses `petros.v2.private-verification-candidate.v1`, without changing the issued-task/private-assessment contract or exporting private fields into browser schemas.

Strict model DTOs contain local keys and evidence, not server UUIDs, origin, reviewer identity, approval or release authority. The server assigns proposal/objective/activity/concept/task UUIDs, immutable concept versions, institution/class/subject/course pins and correction lineage. Bounds: 1–3 objectives, 24 concepts, 48 relationships, depth 2, 24 claims, 12 activities, 12 task metadata candidates, 8 selected source units, 64KiB model output and 96KiB durable draft. Preferences are short optional focus/emphasis and 5–90 minute duration.

Metadata includes exact source binding/revision/original/representation hashes, extractor/interpretation pins, coverage, generator/prompt pins, curriculum revision, actor/timestamps and prior proposal version. Review/release decisions remain authoritative in academic-owner records, projected separately from the draft’s state. `accepted` objective wording is a teacher draft action, not qualified approval.

Hard prerequisite cycles, missing/duplicate identities, foreign local references, invented citations, invalid locators/hashes, unsupported operations/kernels/gestures/editable regions and missing accessibility alternatives fail validation. Every factual definition/claim and instructional candidate goes through M2’s exact reference/quote and deterministic numerical/negation checks. Mechanical checks do not establish semantic entailment. Graph relationships and all generated claims remain review-required.

## H. Teacher editing, lifecycle and concurrency

Objective accept/edit/remove/reorder, claim edit/reject, activity selection/rejection, save, submit-review and withdrawal create immutable preparation versions. Corrections retain previous version, exact editor, command/hash, timestamp, changed fields and revalidation status. The original proposal is preserved. Surviving source references and deterministic content checks are rerun; wording changes cannot self-acquire source support.

Review retries revalidate current qualification before returning an earlier receipt; request hashes include the actual reviewer actor. Release-owner retries also revalidate current reviews before receipt lookup. Expected versions and per-proposal transaction locks fence stale/concurrent edits. Command IDs provide idempotent saves. Two simultaneous saves admit exactly one successor. All edits conservatively detach old review/release dependencies. Submission persists the exact academic candidate **as the author**, before independent review; reviewers cannot fabricate an approved candidate. Source replacement/withdrawal rechecks prevent stale read/review/release. Historical versions are accessible only while current source entitlement permits them.

Review rejection/revision requests remain durable receipts. A draft’s `under_review` state does not imply all review dimensions passed. Superseded source versions are fenced by entitlement; proposal withdrawal is explicit. There is no generic unrestricted patch endpoint.

## J. Qualified assessment separation and privacy

Public proposals contain candidate metadata and opaque status only. Private drafts reuse the existing teaching-pack candidate table and API-only assessment contract fields. They bind exact public proposal hash/version, objective version, criterion/family UUID, immutable source revision/hash, actual reserved native evidence, assistance, origin, correction lineage and immutable private version. They are preparation records, not issued student tasks.

Qualified staff can explicitly prepare or correct a private engineering outline and inspect it through separate `verification/:taskId` routes. These routes require current course/subject qualification, source ownership, staff permissions and a current source; responses are `private, no-store`. Default reference criteria quote the actual reserved unit. Numerical/reference corrections use the same M2 mechanical grounding validator. Private bodies have strict API-only schemas and a 48KiB bound. Private drafts and receipts have current-qualified restricted-role RLS. Existing V1 candidate routes exclude V2 records.

An independent qualified reviewer records a distinct `assessment_instrument` receipt on the exact public candidate, pinning the private family ID/version/hash. Approval requires an explicit **distinct** non-equivalence decision; uncertain/equivalent decisions cannot approve. Being staff, accepting an objective, approving teaching content or supplying an approval field cannot grant this authority. Private author self-approval, wrong versions/hashes, expired/revoked qualifications and forged receipts are denied. Public edits and private revisions invalidate dependent decisions; all nine families must have current approval before aggregate instrument status becomes approved.

A security-barrier projection view exposes only opaque family versions, current-context/review status and qualification pins. Its invoker wrapper delegates current source entitlement to the existing source-live owner and never returns a private body/hash. The view preserves the actual `edrion_app` caller identity required by that existing source policy. Direct private-table reads remain qualified-only. This is a read projection over existing authority records, not another authority store.

The source itself was published in the synthetic fixture: `sourceWasPublished=true` is recorded honestly. Reserving a unit prevents its inclusion in generated teaching context/evidence endpoints; it does not establish freshness against every prior exposure. Mechanical question inequality is only a screen. Real non-equivalence, exposure and defensible alternative criteria require independent subject review. The nine synthetic **distinct** decisions prove the authorization path, not semantic task validity or real academic approval. See [private authorization-path receipt](m3-evidence/private-authorization-path.json).

An additional ordered source-check/content-privacy trigger rejects exact private fragments copied into teaching revisions. It checks source entitlement as the caller before a non-callable owner trigger inspects private rows; failures expose only a rule code and roll back the edit. It excludes criteria already present in the original public candidate and uses normalized token boundaries for both long fragments and short keys. This is deterministic defense in depth, not proof against semantic paraphrase; qualified exposure review remains required. Actual restricted-role tests cover the copy attempt and unchanged draft version. Actual SQL/DTO tests use a private sentinel to verify absence from ordinary proposal responses, source inspection, manifests and the safe projection, including for an unqualified/revoked owner. Private qualified panels are separate from shared public activity previews. Student/cross-tenant/private-source access is denied. No evaluator, answer commitment, official grading receipt, learner evidence or session is created.

Instrument revisions/revocations are rechecked before publication and repeated receipt lookup, including inside SQL manifest admission. Repeat commands are idempotent; material edits cannot inherit authorization. A safe existing-owner projection also returns the recorded manifest ID/version/time after a browser refresh; it explicitly requires current checks again and does not imply student publication. Proposal snapshots remain immutable; review/manifest references are read from their academic owners. No V1 publication behavior is replaced and no V2 student route is enabled.
